- 브랜치: `feature/taxcheck-dashboard-records-api`, 관련 작업 Front #10.

- Backend 계약: PR #7의 `30f4dded7282d64356faf8834f32c2472318be5b`.
  [백엔드 구현 문서](https://github.com/Foreign-In-One/Backend/blob/30f4dded7282d64356faf8834f32c2472318be5b/docs/TAXCHECK_IMPLEMENTATION.md).

  공개 배포 서버에 PR #7이 반영됐다고 가정하지 않는다.

변경은 TaxCheck 화면·전용 API 서비스·입력/응답 검증·테스트·문서에 한정한다.
`services/records-api.ts`에서는 기존 `isPaySummary` 검증 함수를 export해서 재사용한다.
Records/Dashboard 조회 로직과 화면, 공통 상태·프로필·디자인·OCR·백엔드·환경 파일·
의존성·GitHub PR·배포는 바꾸지 않는다.

## 동작

1. 귀속연도와 근로소득/비과세 근로소득을 사용자가 입력하고 확인한다.
   기본값은 한국 시간 기준 직전 완료 연도, 금액은 빈칸, 조건은 미확인이다.
   연도·소득을 수정하면 확인 체크가 해제된다. 현재 연도에는 연중 누계/예상 연봉을
   확정 연간 소득으로 확인하지 말라는 안내를 표시한다.
2. 주택마련저축·무주택·증빙·다른 소득공제 조건을 예/아니요/미확인으로 받는다.
   가입이 미확인/아니요이면 이전 증빙 답은 미확인으로 초기화한다.
3. 사용자가 **분석하고 서버에 저장**을 눌렀을 때만 analyze POST를 보낸다.
   페이지 진입, 다음 단계 이동, 언어 변경, 결과 렌더링은 자동 저장을 하지 않는다.
4. 성공하면 새 ID를 URL의 `taxCheckId`에 반영하고 서버 결과를 표시한다.
   그 주소에서 새로고침하면 GET으로 저장 원본만 조회한다.
5. **가정 변경하기**는 원본 스냅샷에서 시작한다. 귀속연도는 고정이며 가정 확인을
   다시 받는다. simulate POST만 보내고 원본·DB·브라우저 금융 기록은 저장하지 않는다.
   응답 날짜/급여 요약은 원본 분석 당시 자료다. 결과에는 미저장 시뮬레이션임을 표시한다.
6. **저장된 원본 보기**는 저장 당시 결과로 돌아간다. **새 분석 시작**은 빈 입력 화면을
   여는 동작이며, 기존 기록을 삭제하지 않는다.

## 계산·데이터 경계

- 프론트 자체 세무 판정(`evaluateTax`)과 브라우저 결과 자동 저장을 사용하지 않는다.
- 서버의 19% 적용 가정 참고액만 표시한다. 일반세율 예상액/차액은 `null`,
  적용 자격 확정은 `false`다. 환급·실제 납부세액·지방소득세 계산을 추가하지 않는다.
- 입력 미비·미확인·서버 규칙 미검증 연도라면 참고액은 `null`이며 준비 점검만 표시한다.
  현재 백엔드가 참고 계산을 지원하는 연도는 2025·2026이다. 이를 실제 적용 자격으로
  해석하지 않는다. 프론트에 세율 산식이나 추가 연도 규칙을 구현하지 않는다.
- 소득 입력과 `paySummary.totalReceivedPay`는 별개다. 후자는 서버 Paycheck의
  해당 귀속연도 실입금 합계로, 세금용 소득이나 완전한 연봉이 아니다.
- 빈칸은 `null`, 확인된 없음은 `0`. 금액은 정수 13자리/소수 2자리까지 검증한다.
  음수·쉼표·지수 표기·범위 초과는 요청하지 않는다. 소득 합산 상한 검증은 정수 센트로
  수행한다. 금액을 세액으로 계산하는 코드는 없다.
- 카드·분석 설명·근거·경고는 서버 원문이다. UI는 한국어·영어·베트남어·중국어를 지원한다.
  응답 구조, ID/연도/모드, 급여 요약 정합성, 중복 카드, 근거 URL을 검증한다.

## 요청 실패와 중복 저장

API는 15초 제한, 캐시/쿠키 미사용, 자동 재시도/목업 폴백 없음이다.
버튼 동시 클릭은 동기 요청 잠금으로 막고 요청 중 입력/이동 버튼을 비활성화한다.
컴포넌트 해제 시 대기를 중단하고 늦은 응답은 화면에 반영하지 않는다.

분석 POST에서 네트워크 오류·시간 초과·5xx·성공 응답 검증 실패가 나면
**서버에는 이미 저장됐을 수 있다.** 먼저 내 기록을 확인하라는 안내와 중복 위험 확인
체크를 제공한다. 확인 전에는 다시 저장할 수 없다. 입력 화면을 왕복하거나 잘못된
값을 입력해도 이 안내를 우회하지 않는다. 요청 대기 취소는 DB 롤백을 뜻하지 않는다.
이는 사용자 확인 장치이며 백엔드 멱등성을 구현한 것은 아니다.

시뮬레이션 실패 시 저장 analyze로 대체하지 않는다. 원본은 보존한다.
GET 실패는 별도 오류와 GET 재시도를 제공한다. 원본이 없다고 임의 판정하지 않는다.

## 노트북에서 새 흐름만 확인

이미 통과한 Records/Dashboard 전체 수동 테스트를 처음부터 반복할 필요는 없다.
로컬 통합 백엔드를 18080으로 실행하고, Front에서 `pnpm dev` 후 터미널 Local 주소의
`/taxcheck`를 연다. 3000/3001을 모두 실행할 필요는 없다.

1. **기존 조회**: `/taxcheck?taxCheckId=1`에서 기존 가상 TaxCheck 1의 저장 결과가
   조회되는지 확인한다. GET이므로 새 기록이 생기면 안 된다.
2. **신규 저장**: 새 분석에서 귀속연도 2026, 가상 총급여 30,000,000원,
   가상 비과세 2,000,000원, 확인 체크로 저장한다. 2026년 값은 이전 테스트를 재현하는
   가상 데이터일 뿐 실제 연간 확정 소득이라는 뜻이 아니다. 참고액 6,080,000원,
   일반세율/차액 미계산, URL에 새 ID가 표시돼야 한다. ID를 1로 가정하지 않는다.
3. **새로고침**: 새 ID 주소를 새로고침해도 동일한 ID/저장 결과이며 중복 저장하지 않는다.
4. **시뮬레이션**: 가정 변경에서 총급여 40,000,000원으로 바꾸고 가정 확인 후 실행한다.
   비과세 2,000,000원이 유지되면 참고액 7,980,000원, 미저장 안내가 나와야 한다.
   원본 보기는 6,080,000원으로 돌아오고 새로고침도 원본을 조회해야 한다.
5. **연결 확인**: 내 기록/Dashboard 새로고침 후 신규 분석 1건만 추가되고
   시뮬레이션 때문에 기록이 추가되지 않는지 확인한다. 기존 2건이었다면 저장 후 3건,
   시뮬레이션 후에도 3건이다. 그동안 팀원이 공유 데이터를 바꿨다면 수는 달라진다.

실제 문서/개인정보 대신 가상 자료만 사용한다. 공유 사용자 1은 개인정보 격리 기능이 아니다.
DB 삭제·데모 초기화·실제 업로드는 이 확인에 필요하지 않다.
